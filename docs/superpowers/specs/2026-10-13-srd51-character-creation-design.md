# SRD 5.1 一级角色创建设计

日期：2026-10-13

状态：待用户核对

依据：[SRD 5.1 CC BY 4.0](https://media.dndbeyond.com/compendium-images/srd/5.1/SRD_CC_v5.1.pdf)、[项目设计](../../design.md)、[事件契约](../../data-contract.md)

## 目标与范围

玩家在 Codex 聊天中按 2014 版 SRD 5.1 创建一级角色，而非只能使用预设的人类战士。M2 的建卡完成条件是：SRD 5.1 收录的一级种族／亚种族、职业、一级必须作出的职业选择、侍僧背景及其明确允许的自定义、起始装备和合法施法选择均可查询、选择、校验并形成可保存的角色卡。人类战士＋侍僧保留为纵向游玩和回归测试样例，不是唯一可建角色。

这不是完整《玩家手册》授权清单。SRD 5.1 未收录的官方选项不伪装成内置规则；当前版本没有的内容返回明确的 `unsupported_option`，并说明 SRD 边界。一级以上的成长、多职业和后续等级资源属于 M3。扩展包不在此范围。

M2 只有在所有可创建角色的一级核心资源与行动也能被游玩系统正确处理时，才可标记为可玩；不能让玩家创建一个法师，却只实现战士战斗。完整一级建卡可先作为独立的中间交付，但 README 必须明确当时尚不可游玩。

## 方案选择

采用“版本化规则目录＋纯角色计算器＋战役事件服务”。不用把每个职业的规则散写在 `character.py` 的条件分支中，也不提前建设能运行任意未来扩展包的通用规则解释器。共同公式由计算器执行；每个种族、职业、装备、法术的可选项和效果由经测试的 SRD 数据定义。不能数据化的特殊一级规则使用按稳定规则 ID 注册的小型专用处理函数，不能由 Codex 临时猜数值。

## 数据与模块边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| `data/character-options.json` 及分表 | 稳定选项 ID、一级选择约束、来源规则 ID、种族与职业收益、装备和法术引用；目录带 `schema_version` 与 `ruleset` | 玩家状态、随机数、叙事文本 |
| `scripts/character.py` | 列出可选项、验证选择、计算一级角色的完整机械卡；同一合法输入必得同一输出 | 掷骰、写存档、编造缺失的选项 |
| `scripts/dice.py` | 为掷属性生成六组 `4d6` 原始点数 | 舍骰规则裁定、角色卡和事件提交 |
| `scripts/state.py` | 为一次建卡意图分配并校验 `operation_id`，保存掷属性记录和最终 `character.created` 事件，处理重试 | 自行重算随机点数、修改规则目录 |
| Codex Skill 工作流 | 分步询问玩家选择、说明规则来源、展示错误与预览 | 绕过脚本直接写入数值、替玩家决定未授权的选项 |

目录还需一份可审计的选项清单：每个 SRD 一级选项对应来源章节、目录记录和至少一个测试；没有相应记录时不得把覆盖矩阵标为完成。只保存必要的结构化数值与简短名称、说明，保持 CC BY 4.0 署名，不复制非 SRD 官方文本。

## 建卡输入与流程

1. `options` 接口按已选种族／职业等上下文返回当前合法选项、必选数量、互斥关系、规则来源和清楚的中文提示。返回稳定 ID；显示名称可翻译，但存档不靠译名识别规则。
2. 属性生成方式为标准数组、六次 `4d6` 取最高三颗，或经玩家选择的 SRD 27 点购点变体。标准数组为默认建议，玩家自行把 `15、14、13、12、10、8` 一一分配给六项属性。购点使用 SRD 的 8–15 成本表且总成本不超过 27；种族加值在基础分配之后应用。
3. 掷属性时，事件服务先按操作 ID 检查已有结果，再调用 `dice.py` 六次，并把六组结果作为同一个 `character.ability_scores_rolled` 事件提交。每组保存四颗原始骰值、舍弃索引、三颗保留值与合计。玩家随后自由分配已掷出的六个数；重复请求同一操作只能读回旧结果。角色计算器只接受事件服务核验过的掷骰引用，不能把玩家提交的任意六个数冒充已掷结果。
4. 玩家选择 SRD 所含种族／亚种、职业、侍僧或其 SRD 允许的自定义方式、技能与工具熟练、语言、职业一级特性、起始装备；施法职业还须选择其一级规则允许的戏法、已知或准备法术及其他施法选项。重复熟练按 SRD 替代规则处理，不叠加双倍熟练。
5. 姓名、个人经历和性格描述是玩家自由文本，可留空、自己写或由 Codex 协助构思。它们不能生成额外属性、熟练、物品或法术。只有经校验的规则选项进入机械计算。
6. 先展示候选角色卡和未完成／无效选择；玩家确认后，事件服务一次性提交 `character.created`。确认前可修改选择；确认后改变机械项须走明确的后续规则或重建流程，不直接改 JSON。

## 输出与存档契约

`character.py build` 接收版本化 JSON 输入，输出 `schema_version`、`ruleset`、`catalog_version`、`source_choices`、`rule_ids`、`derived` 和 `resources`。`derived` 至少含属性与调整值、熟练加值、技能和豁免、AC、速度、最大 HP、命中骰、装备与攻击能力；施法角色另含施法属性、法术攻击／豁免 DC、已知／准备法术及一级法术位。`resources` 为可消耗的职业能力、生命值和法术位提供明确的最大值与初始值，不使用“字段缺失＝尚未加载”的语义。

`character.created` 事件保存玩家选择、规则目录版本、掷属性事件引用（若有）、计算结果与公开角色摘要。`state.json.character` 使用同一结果。重放依事件中已确认的选择与数值确定性进行，绝不重掷；目录升级不得静默改变既有战役角色，需版本检查及显式迁移。聊天和面板只读已提交的公开投影。

## 错误处理与验证

机器接口使用稳定错误码：`invalid_choice`（选择值或数量不合法）、`missing_choice`、`unsupported_option`、`invalid_ability_method`、`unverified_roll`、`ruleset_mismatch`。错误包含具体字段与可选项提示，不把失败的候选卡提交为战役事件。输入 JSON 大小、自由文本长度及嵌套深度要设上限；不执行玩家输入中的代码，也不加载未经批准的外部规则包。

测试先覆盖共同公式与三种属性方式，再逐项覆盖每个 SRD 一级种族／亚种、职业起始熟练与资源、职业选择、侍僧及自定义限制、起始装备和施法选择。还需交叉测试至少一名施法者与人类战士的完整角色卡，验证非法混搭、重复选项、越界购点、伪造掷骰、超范围内容和事件重试。验收清单以 SRD 5.1 来源索引逐项对账，而非只靠几个成功样例。测试对随机数注入固定值，不要求生产掷骰可预测。

## 实施顺序与完成标准

1. 建立一级 SRD 选项目录和来源／测试清单，优先做共用属性、熟练、装备与侍僧规则。
2. 完成标准数组与购点的纯计算和校验，再接入有事件凭据的 `4d6` 掷属性。
3. 按职业逐类接入一级选择和输出；每类入库前通过本类规则测试。同步扩充种族／亚种、装备和一级可选法术数据。
4. 接入战役创建与 `character.created`，验证确认、重试、恢复及面板公开投影。
5. 所有 SRD 一级建卡选项覆盖并经测试后，才宣布“一级建卡完成”；所有可建角色的一级规则能实际游玩后，才宣布 M2 可玩。

用户已确认以 SRD 5.1 全量一级建卡取代单一角色模板、默认提供可自行分配的标准数组、以版本化规则数据和纯计算器实现，并使所有随机数可追溯。未收录的官方内容与后续等级不在本规格的完成声明内。
