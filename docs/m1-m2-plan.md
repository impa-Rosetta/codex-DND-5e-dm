# Codex 5e DM：M1–M2 实施计划

日期：2026-10-13  
依据：[单人冒险 Skill 设计规格](design.md)

## 目标与交付边界

这份计划把第一阶段产品的前两个里程碑落实到文件、任务和验收。M1 建立可信的 SRD 5.1 规则与数据基础；M2 跑通一段真实的单人冒险，并在 Codex 聊天旁显示同步的原创网页面板。M2 是可玩纵向版本，完整 SRD 5.1 的 1–20 级内容覆盖与正式发布仍由 M3、M4 完成。玩家扩展包不进入本计划。

开发源码放在当前工作区的独立项目目录 `work/codex-5e-dm/`，创建其自己的 Git 仓库，避免把项目提交到上层目录的仓库。此文档及面向用户的阶段性交付保存在 `outputs/`。实际编码开始前检查该目录是否已有用户文件；若已有，不覆盖。

## M1：规则基线与接口契约

### 1. 建立授权与规则来源清单

- 以 [SRD 5.1 CC BY 4.0 原文](https://media.dndbeyond.com/compendium-images/srd/5.1/SRD_CC_v5.1.pdf)为唯一内置规则正文来源，记录下载版本、官方 URL 和所需署名。项目源码重新编写，不复制参考仓库的 AGPL 代码。
- 在 `docs/srd-coverage.md` 中列出建卡、属性与熟练、探索检定、战斗、装备、法术、怪物、休息、升级、死亡规则等条目。每项记录 SRD 章节、M2 是否需要、结构化状态、测试状态和 M3/M4 完成状态。
- `rules-index.json` 为每条内置规则保存稳定 ID、SRD 章节及适用版本。对未收录的官方内容返回“当前规则数据不含此项”，不推断数值。

**验收**：能从任意 M2 机械裁定追到 SRD 条目；覆盖矩阵清楚显示 M2 子集与正式成品的差距；授权说明可用于最终发布。

### 2. 定义统一事件和存档格式

- 在 `docs/data-contract.md` 定义 `manifest.json`、`state.json`、`world.md`、`events.jsonl` 的字段、版本号、角色 ID、战斗者 ID、事件 ID 和时间顺序。
- 事件至少覆盖角色创建、玩家声明、旁白、掷骰、裁定、资源变化、位置变化、地图发现、回合推进。区分 DM 私有事件与可向玩家展示的事件，避免地图泄露未发现地点。
- 明确事务顺序：验证操作 → 生成唯一事件 ID → 持久化完整事件 → 原子替换状态快照。快照记录最后应用的事件 ID；加载时只重放未应用事件，拒绝损坏记录并保留可恢复副本。
- 在 `docs/decisions.md` 写明一处规则的解释优先顺序：SRD 原文、明确记录的玩家家规、DM 对开放情境的裁定。家规不能默默改变。

**验收**：用纸面样例证明一次攻击导致的骰值、伤害、生命值、聊天反馈和面板事件都指向同一个事件 ID；中途失败后重放不会重复扣血。

### 3. 确定 M2 最小内容与本地运行条件

- M2 先支持 SRD 5.1 收录的全部一级建卡选项；1 级人类战士、侍僧背景、基础装备、一个 SRD 怪物和原创开局保留为完整纵向测试样例，而非唯一可建角色。一级以上成长仍由 M3 完成。详细边界见[一级建卡设计](superpowers/specs/2026-10-13-srd51-character-creation-design.md)。
- 本地执行先以 Python 标准库为基线，桌面面板用只监听 `127.0.0.1` 的轻量 HTTP 服务和实时事件流；不依赖云服务或额外 API key。实施时验证当前 Codex 桌面环境是否提供可运行的 Python，并把缺少运行时的提示写入安装说明。
- 浏览器面板负责展示，游戏行动只从 Codex 聊天进入。Codex 桌面可打开本地 URL 时自动在旁边打开；其他环境输出 URL。

**验收**：在干净环境中能运行一个骰子命令、启动本地页面、访问状态快照；缺少 Python 时错误信息清楚且不修改战役数据。

## M2：可玩纵向流程

### 4. 实现骰子服务

- `scripts/dice.py` 支持 M2 所需骰式：`d20`、`NdS`、常数修正、优势/劣势；返回每颗骰子、保留值、修正、总值和用途。拒绝零面骰、过大骰量和无效语法。
- 随机源仅在此模块使用；其他脚本通过该模块获取骰值。测试时可注入固定骰值，不把测试随机性写入正式战役。
- 单元测试覆盖优势/劣势、加减值、边界、错误输入，以及自然 20/1 只由具体规则解释的行为。

**验收**：同一输入格式可从 CLI 获得机器可读结果；所有 M2 掷骰在事件日志中可追溯原始点数。

### 5. 实现角色与单人基础战斗

- `scripts/character.py` 按 SRD 5.1 全部一级建卡选项校验玩家选择，计算属性调整值、熟练加值、AC、生命值、速度、技能、豁免、一级职业资源与施法数据；个人往事为可选文本，不产生未经批准的数值奖励。目录与脚本逐类实现、逐类验证；只完成一类不得宣称建卡完成。
- `scripts/combat.py` 处理先攻、回合顺序、移动距离、动作、附赠动作、反应、近/远程攻击、命中、伤害、生命值变化与战斗结束。位置以 5 英尺坐标记录，面板只展示文字战斗状态。
- M2 的规则之外但合理的玩家行动由 Codex 按 SRD 裁定；脚本不认识的机械操作返回明确错误或待裁定状态。普通聊天不能直接写入机械数值。
- 规则测试使用固定骰值覆盖命中、未命中、自然 1、自然 20、重击、临时生命值及回合资源重置；逐类验证所有可创建角色的一级核心能力。一次测试应通过最终状态验证行为，不只匹配文案。

**验收**：所有可创建的一级角色都能使用其一级核心规则游玩；人类战士样例能完成至少一场一对一遭遇，同一次攻击的数学结果、最终 HP、事件日志和面板完全一致。

### 6. 实现战役创建、加载与恢复

- `scripts/state.py` 创建战役目录与初始文件，校验路径和格式，按 M1 契约提交事件与快照；存档永不写进 Skill 安装目录。
- 新战役生成原创起始地点、可行动的冲突、至少一名 NPC 和一处可发现地点。Codex 的叙事只确立玩家可观察的事实；私有设定保存在不暴露给面板的文件或字段。
- 加载战役时核对规则版本、角色资源、当前位置、地图已发现节点及最后事件；给出简短回顾。对损坏快照、重复事件和中断提交做恢复测试。

**验收**：退出当前聊天后重新加载战役，可继续完成尚未处理的场景；不会重复应用上一回合，也不会泄露尚未发现地点。

### 7. 编写 Skill 工作流并验证触发

- `SKILL.md` 仅保留名称、准确的触发描述、支持的玩家意图及“何时读哪份参考说明”。详细建卡、一般裁定、战斗和存档流程放入 `references/`。
- 明确 DM 不替玩家行动、不捏造骰值、数值以脚本为准、需要检定时先说明依据、关键事件提交后再叙述为事实。提供开始新战役、加载、查看状态、结束会话的自然语言入口，不依赖 Claude 插件专有命令。
- 用直接请求、含糊请求和非游戏请求测试 Skill 是否正确触发；再用一段真实对话核查脚本调用顺序与状态更新。

**验收**：新 Codex 会话能发现并使用 Skill，按示例提示完成建卡及一段冒险；无关请求不会误进 DM 模式。

### 8. 实现侧边栏冒险面板

- `display/server.py` 只提供静态页面、经筛选的战役快照和实时事件；连接丢失后客户端重新拉取快照，不以浏览器内存或 `localStorage` 为权威状态。
- `display/web/` 先完成适合 Codex 窄侧栏的布局：当前场景、角色卡、掷骰记录、战斗顺序。M2 的探索地图显示起始地点和已发现节点；完整地图视觉设计在 M4 完成。
- 页面可以查看与展开信息，但没有“提交行动”输入框。Skill 在战役加载时启动或复用本地服务，并请求打开桌面浏览器面板；若面板无法打开，聊天游玩照常进行。
- 浏览器验收包括首次加载、一次掷骰、HP 变化、地点发现、刷新、断线重连及窄侧栏布局。

**验收**：玩家只在 Codex 聊天中输入；侧栏在同一次已提交事件后显示一致的角色和场景状态；刷新后不丢失信息。

### 9. 完成纵向游玩验收

- 使用一名新建 1 级角色，依次完成：创建战役 → 与 NPC 交谈 → 探索并检定 → 揭示地图地点 → 战斗 → 保存退出 → 新会话加载 → 继续行动。
- 对每一步保存事件 ID、骰值、资源变化和面板截图或检查记录。出现不一致先修复数据契约或状态转移，再调整叙事文案。
- 在 `README.md` 写清 M2 当前覆盖、未覆盖的 SRD 内容、启动方法与实际示例，避免把纵向版本称作完整成品。

**验收**：上述流程在 Codex 桌面应用中由新会话完整跑通；规则测试、恢复测试和界面检查通过。M2 通过后再计划 M3 的完整规则覆盖。

## 关键依赖与推进顺序

```text
M1 规则来源与覆盖矩阵
        ↓
M1 数据/事件契约 ──→ M2 存档服务 ──→ M2 Skill 游玩流程
        ↓                    ↓                 ↓
M2 骰子与角色/战斗规则 ──────┘             M2 端到端验收
                             ↓                 ↑
                       M2 侧边栏面板 ──────────┘
```

骰子、存档和网页可分别开发，但它们应在 M1 的事件契约稳定后再连接。M2 冒险测试通过只是开始覆盖 M3 的条件，不能替代正式成品的完整性检查。

## 明确的暂停条件

- 若官方 SRD 5.1 不含某项拟内置内容，暂不加入规则数据；记录到覆盖矩阵并设计原创替代或等待玩家选择。
- 若当前 Codex 环境无法稳定在侧边栏打开本地服务，先保留可运行的本地 URL 和聊天游玩，记录具体平台限制，再决定桌面适配方式。
- 若实测发现 M2 的状态/事件格式无法承载升级、法术位或扩展包启用，不继续叠加功能；先修订数据契约与迁移方案。
